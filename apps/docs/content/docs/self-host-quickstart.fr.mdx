Cette documentation concerne l’édition personnalisée. Utilisez ce checkout ou les artefacts fournis par votre responsable de déploiement ; les paquets applicatifs du projet d’origine ne contiennent pas ces modifications.

## Démarrer une instance personnelle

Avec Docker Compose 2.30 ou ultérieur, utilisez le [script d’installation du dépôt](https://github.com/wsshow/multica/blob/main/docs/integrated-image.md#personal-deployment) pour démarrer la dernière version stable compatible avec le déploiement personnel. Ouvrez `http://localhost:8080` et saisissez le code à usage unique affiché dans le terminal. Créez le compte administrateur pour ouvrir votre espace de travail personnel.

Docker Compose gère PostgreSQL. Les pièces jointes et clés de signature sont stockées localement. Vous pouvez démarrer sans fichier d’environnement ni service de messagerie. Pour compiler et démarrer depuis le checkout actuel, utilisez `make integrated-personal-build`.

## Préparer les sources

Utilisez un checkout personnalisé validé ou une archive fournie par son responsable. Préparez le plugin Docker Compose, Make et OpenSSL. Les outils d’agent et leurs comptes se préparent séparément sur les ordinateurs d’exécution.

## Démarrer les services

Exécutez depuis la racine du dépôt. Si `.env` est absent, la commande crée la configuration et les secrets initiaux, construit `multica-backend:dev` et `multica-web:dev` depuis ces sources puis démarre PostgreSQL, API et Web. La configuration et les volumes existants sont conservés. Vérifiez les secrets déjà présents.

```bash
make selfhost-build
docker compose -f docker-compose.selfhost.yml ps
curl -fsS http://localhost:8080/readyz
```

Web: `http://localhost:3000` · API: `http://localhost:8080`

## Se connecter

Ouvrez votre URL Web et connectez-vous avec un code e-mail. La livraison en production nécessite votre propre SMTP ou Resend et un domaine expéditeur. Sans fournisseur de courrier, le backend actuel écrit les codes générés dans ses journaux. Un code fixe exige `APP_ENV=development` et ne convient pas à un déploiement public. Google nécessite votre propre configuration OAuth.

## Connecter Desktop

Utilisez le paquet Electron personnalisé, copiez `apps/desktop/desktop.example.json` vers `~/.multica/desktop.json`, modifiez les deux URL et redémarrez. Sans configuration, aucune connexion n’est établie. `wsUrl` peut remplacer l’URL WebSocket dérivée de l’API.

```json
{
  "schemaVersion": 1,
  "apiUrl": "http://localhost:8080",
  "appUrl": "http://localhost:3000"
}
```

## Connecter un autre ordinateur

Construisez le CLI depuis les mêmes sources personnalisées, placez ce binaire dans PATH puis connectez-le explicitement. Desktop inclut son CLI : aucune installation séparée n’est requise pour son runtime géré. Un outil d’agent pris en charge doit être installé et authentifié sur l’ordinateur d’exécution.

```bash
go -C server build -o bin/multica ./cmd/multica
```

```bash
multica setup self-host --server-url http://localhost:8080 --app-url http://localhost:3000
multica auth status
multica daemon status
```

## Accès distant

L’exemple Compose lie les ports à `127.0.0.1`. Pour un accès distant, utilisez un proxy inverse TLS et configurez vos propres `FRONTEND_ORIGIN`, `MULTICA_APP_URL`, `MULTICA_PUBLIC_URL`, `CORS_ALLOWED_ORIGINS` et URL de fichiers. Dans Desktop, `localhost` désigne l’ordinateur Desktop. Configurez les routes d’authentification, de santé et WebSocket, puis vérifiez depuis l’ordinateur d’exécution.

## Sauvegardes et mises à jour

Sauvegardez PostgreSQL, les fichiers, les secrets et la révision déployée. Pour un déploiement source, sélectionnez un commit personnalisé validé puis relancez `make selfhost-build`. Pour vos images publiées, configurez `MULTICA_BACKEND_IMAGE`, `MULTICA_WEB_IMAGE` et un `MULTICA_IMAGE_TAG` immuable, puis utilisez `make selfhost`. Cette cible télécharge les images configurées sans construire les sources. Ne remplacez pas cette édition par les artefacts `latest` d’origine. Un ancien conteneur n’annule pas les migrations de base de données.

```bash
docker compose -f docker-compose.selfhost.yml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > multica-backup.sql
```

## Kubernetes

Utilisez le chart source `deploy/helm/multica`, vos images et les Secrets décrits dans `values.yaml`. Les images doivent être accessibles à tous les nœuds. Les valeurs par défaut sont des images locales `:dev` avec `IfNotPresent` ; un redémarrage seul ne change pas de version. Aucun chart OCI du projet d’origine n’est nécessaire.

```bash
helm upgrade --install multica ./deploy/helm/multica --namespace multica
```

## Vérification

Vérifiez `/readyz`, connexion, enregistrement du runtime, résultats des tâches et pièces jointes. `/health` ne confirme que la vie du processus. Télémétrie, rapports de plantage, rapports anonymes et métriques opérationnelles sont désactivés ; `/metrics` et `/health/realtime` sont indisponibles. Usage, coûts, historique et état en ligne visibles restent disponibles.

```bash
make selfhost-stop
```
